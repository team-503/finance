# Монорепо finance

pnpm workspaces + Turborepo. Node 24 (`.nvmrc`), pnpm 11.

## Розкладка

| Шлях                         | Що це                                                      |
| ---------------------------- | ---------------------------------------------------------- |
| `apps/web`                   | фронтенд на Next.js, порт 3000                             |
| `apps/api`                   | бекенд на NestJS, порт 3001 (змінна `PORT`), збірка на SWC |
| `packages/types`             | `@repo/types` — інтерфейси, спільні для web і api          |
| `packages/eslint-config`     | `@repo/eslint-config` — `base`, `next-js`, `node`          |
| `packages/typescript-config` | `@repo/typescript-config` — `base`, `nextjs`, `nestjs`     |

Бекенд віддає `GET /healthcheck` через `@nestjs/terminus`, модуль лежить у `apps/api/src/health`.

## Команди

Запускай з кореня — turbo розкидає по пакетах і кешує.

```sh
pnpm dev          # усі застосунки у watch-режимі
pnpm build
pnpm lint
pnpm typecheck
pnpm format       # prettier по всьому дереву
```

Звузити до одного пакета:

```sh
pnpm build --filter=api
pnpm dev --filter=web
```

## Граблі

**Тестів немає.** Дивись `.claude/rules/testing.md`. Не додавай тестових файлів, раннерів і задачі `test`. `apps/api/vitest.config.ts` лежить готовим на майбутнє — не чіпай його і не заводь навколо нього скриптів.

**SWC не перевіряє типи.** `nest build` лише транспілює, тож зламаний тип доїде до `dist` мовчки. `pnpm typecheck` — єдина перепона, ганяй його перед тим, як вважати зміну в бекенді завершеною.

**TypeScript розділений навмисне.** Репо на TS 7, але `apps/api` прибитий до TS 6: Nest CLI потребує програмного API компілятора, яке TS 7.0 викинув, а TS 7.1 обіцяє повернути. Не зводь версії до однієї, доки це не станеться.

**Nest 12 — це ESM.** `apps/api` має `"type": "module"`, тому відносні імпорти пишуться з розширенням `.js` (`./health.module.js`), навіть коли файл насправді `.ts`. `.swcrc` віддає `es6`-модулі, щоб збігалося.

**Terminus оголошує не той діапазон peer-залежностей.** `@nestjs/terminus@11.1.1` просить Nest `^10 || ^11`, а в нас 12. `pnpm peers check` свариться, застосунок працює. Прибери попередження, коли terminus випустить версію під Nest 12.

**`base.json` не прив'язаний до платформи.** У ньому немає `DOM`; `DOM` і `DOM.Iterable` додає `nextjs.json`. Не тягни браузерні типи в базу, інакше бекенд почне бачити `document`.

**`@repo/types` — компільований пакет.** Він віддає `dist` через `tsc`, споживачі читають `dist/*.d.ts` і `dist/*.js`, а не сирці. Якщо навести `exports` на `src/*.ts`, воно теж збереться і навіть запуститься — але лише тому, що Node роздягає типи на льоту, тобто в продакшн поїде сирий `.ts` і надія на стриппер. Збирай. Порядок задає turbo через `dependsOn: ["^build"]`.

**`tsc` — єдиний збирач для пакетів.** Ніякого rollup чи tsup. Бандлер потрібен, коли пакет публікується в npm, коли треба подвійний вихід ESM/CJS або коли в пакеті є ассети, яких `tsc` не вміє. Жодне з цього не про приватний пакет усередині воркспейсу.

**Один лінтер, один форматер.** ESLint скрізь (Nest 12 за замовчуванням ставить oxlint — його прибрано), один кореневий `.prettierrc.yaml`: ширина 120, 4 пробіли, одинарні лапки, без крапок з комою. Файли eslint у пакетах лише реекспортують пресет із `@repo/eslint-config`.

**Читання змінної оточення коштує рядка конфіга.** `turbo/no-undeclared-env-vars` валить лінт, доки змінна не з'явиться в `turbo.json` у полі `env` відповідної задачі.

**Нативні postinstall заблоковані за замовчуванням.** pnpm не запускає build-скрипти, доки пакет не внесений у `allowBuilds` у `pnpm-workspace.yaml`. `@swc/core` там уже є, наступний такий додавай туди ж.

**Перед комітом працює husky.** `.husky/pre-commit` кличе `lint-staged`, налаштування — у `.lintstagedrc.yaml`. Розкладка така: `.ts/.tsx` проходять eslint, prettier і `pnpm typecheck`; решта коду — eslint і prettier; усе інше — просто prettier. Групи не перетинаються, тож один файл ніколи не потрапляє під дві команди одночасно.

**`sh -c 'pnpm typecheck'` у lint-staged написано так навмисне.** lint-staged дописує імена застейджених файлів у кінець кожної команди, а `typecheck` їх не приймає. Обгортка ковтає зайві аргументи як `$0`, `$1` і запускає задачу без них. У JS-конфігу це була б функція, але конфіги ми тримаємо в yaml.

**У корені лежить `eslint.config.mjs`.** ESLint 10 шукає конфіг від розташування файла вгору, а не від cwd, тож пакети й далі лінтуються своїми конфігами. Кореневий потрібен тим файлам, над якими пакета немає — без нього lint-staged падає на них із помилкою про відсутній конфіг.

**`.prettierignore` тримає лок-файл, збірки й генероване.** Без нього `prettier --write .` переформатовує `pnpm-lock.yaml` і `next-env.d.ts`, а це шум у кожному diff.

## Як додати пакет

1. `packages/<назва>/package.json` — ім'я `@repo/<назва>`, обов'язково `private`.
2. У `tsconfig.json` успадкуй пресет, у `eslint.config.mjs` реекспортуй конфіг.
3. Додай скрипти `lint` і `typecheck`; `build` — лише якщо зібраний вихід потрібен комусь ззовні пакета.
4. `pnpm install`, щоб воркспейс підхопив.
